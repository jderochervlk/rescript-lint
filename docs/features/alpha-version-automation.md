## Supported repository behavior

`npm/package.json` owns the current version. Only `0.1.0-alpha.N` is supported,
with a canonical nonnegative safe-integer counter. Other base versions, stable
versions, leading zeroes and other channels fail closed. `publishConfig.tag`
must remain `alpha`. This is deliberately not a general release framework.

From the repository root, using Node 24+ and the existing Opam switch:

```sh
node scripts/version/cli.mjs check
node scripts/version/cli.mjs dry-run 3
node scripts/version/cli.mjs update 3
node --test test/version/*.test.mjs
```

The count is the number of unprocessed source PR merges, not a desired counter.
The check validates the manifest, Dune version, CLI version, generated Opam
version, and exact CLI and LSP transcript expectations. The updater validates
everything first, generates Opam metadata with Dune in a temporary isolated
project inside the workspace, then writes the five files. A generation or
validation failure writes none of the source files. Caught write failures
attempt rollback; a process kill or filesystem failure during writes is not an
atomic transaction. Discard that working tree and retry from trusted main.
Automation avoids that local write window by committing a complete Git tree.

The dry run reports old/new versions, merge count and changed paths without
writing or invoking Dune. Historical examples and plans are not rewritten.
Native versions and launcher exact optional dependencies continue to derive
from the npm manifest in the existing packaging code.

### Windows metadata regression (2026-10-22)

The first five-target PR run exposed a Windows updater failure after successful
toolchain setup. Dune appends the Opam template verbatim, while source version
reads already normalize CRLF to LF. Copying a CRLF template unchanged therefore
produced three extra carriage returns in generated `pin-depends` metadata.
This was reproduced with real pinned Dune on Linux: 1,179 generated bytes
versus 1,176 expected bytes, equal after CRLF normalization. The updater now
normalizes the template input consistently before generation and still requires
exact generated metadata equality. Real-Dune tests cover LF, CRLF, and rejected
substantive template drift with no source writes.

A separate intermittent `setup-ocaml` release-discovery failure was initially
suspected to require a pagination patch. That diagnosis was not established:
healthy unpaged and explicitly paged API requests later returned identical
releases, and upstream had already addressed a related transient failure.
No installer replacement, dependency fork, or signature/version-policy
weakening was made. The Windows failure above is independent of that transient
setup problem.

Read-only PR/main and native build CI runs consistency and regression tests.
Every native build also checks the built executable, tag (if present) and source
versions. Direct staging validates source consistency and alpha policy before
requesting OIDC or staging any tarball. Manual dispatch obeys the same guards.
No version update creates a tag, stages, publishes, approves, or moves `latest`.
The shared workflow also retains the
[failure-only hosted Opam observer](opam-discovery-diagnostics.md).
Its diagnostic requests do not replace successful setup, relax any gate, or
establish what the preceding action's own API response contained.

## Reconciliation protocol

The [workflow](../../.github/workflows/alpha-versions.yml) runs only when
`VERSION_AUTOMATION_ENABLED` is set to `true`, the workflow ref is main, and
the event is either a `push` to `main` or manual dispatch from main.
The push trigger is branch-filtered: other branches, tags and PR events do
not start reconciliation. The job also checks an explicit push/manual event
allowlist. Unset/false opt-in and dispatches from other refs do not run the
privileged job. Deployment alone is not opt-in.
It serializes all runs and checks out **only trusted current main**, with full
history and no persisted credentials. It never executes PR head code or
interpolates PR titles/bodies into shell.

Main pushes are wake-up signals, not version increments. The reconciler still
enumerates merged PRs and uses its checkpoint to determine the count. A direct
main commit without a newly merged source PR does not bump the version.
Registered version-PR merges are excluded even if their main push triggers a run.

This replaces the earlier `pull_request_target: closed` trigger. It does not
need PR payloads or fork-code access, and avoids GitHub's
[default restriction on that event in public repositories](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target#default-policy-for-pull_request_target),
enforced from December 2, 2026. No Actions policy exception or broader token
permission is needed. Existing warnings remain attached to historical runs;
main-push delivery must be verified on a new run after deployment.

The workflow uses the automatically generated repository `GITHUB_TOKEN`,
passed to `gh` as `GH_TOKEN`. Only the reconciliation job requests Contents
write and Pull requests write. Default permissions and ordinary build jobs
remain read-only. There is no custom GitHub App, private key, personal access
token, bot-login variable, or credential-generation action to configure.
The adapter rejects missing repository/token configuration, execution outside
GitHub Actions, and workflow refs other than `refs/heads/main`.

The [API process adapter](../../scripts/version/github-api.mjs#L2) passes a
copied environment with `CLICOLOR_FORCE=0` and `NO_COLOR=1` to each `gh api`
child. Machine-readable JSON must not inherit color preferences from toolchain
setup. Credentials, host, other environment settings, methods and stdin JSON
bodies are preserved; the parent environment and human-readable tool logs are
unchanged. JSON parsing remains strict, including for unexpected ANSI output.

The adapter enumerates **all** PR pages. Git ancestry filters merged PRs between
the committed bootstrap baseline and the current main snapshot. No timestamp
watermark, triggering-event counter, commit-message convention, or search API
result limit determines eligibility. Documentation, refactoring, and ordinary
bot-authored PRs count too. Closed-unmerged and wrong-base PRs do not.

`.github/alpha-version-state.json` records source PR IDs and automation PR IDs.
Its initial baseline is main at implementation start (`59850f4`); the
implementation PR and subsequent ordinary merges count when activated. Changing
that bootstrap boundary requires an explicit reviewed migration.

An excluded version PR must have a recorded ID **and** the `github-actions[bot]`
author, exact same-repository `automation/alpha-version` head, and main base.
An owned but unregistered merged PR stops reconciliation for inspection rather
than silently looping or losing a merge. Labels, titles and bot authors alone
are not exclusion evidence.

One pending owned PR aggregates all sources absent from main's checkpoint. Its
counter is recomputed from main, never incremented from the pending branch.
The workflow creates a draft first and commits its PR ID into the checkpoint
before making it ready or requesting auto-merge. Retries after any accepted mutation
recover the branch/PR and reuse the same counts. Duplicate deliveries make no
new version commit. Coalesced Actions events cannot lose merges because every
run enumerates main history again.

The adapter keeps [`run`](../../scripts/version/reconcile-run.mjs#L160) as a short
asynchronous orchestration boundary. The CLI and adapter tests await its promise.
Named internal phases
load the trusted snapshot, verify the owned branch, compare fresh refs, commit a
complete Git tree, register the draft checkpoint, and make the PR ready before
requesting auto-merge. Branch heads are passed and returned explicitly rather
than hidden in nested mutable closures. This structure was revised after Codex
review on 2026-10-22; accepted-mutation interruption tests exercise the same
ordering and recovery guarantees.

Branch commits require the bot author and either the bot committer or GitHub's
`web-flow` committer with `verified=true` and `reason=valid`, enforced by
[`ownedCommit`](../../scripts/version/reconcile.mjs#L22). Other authors,
committers, unverified `web-flow` commits and unexpected changed files are
rejected. Commit metadata does not replace the registered PR-ID and exact
repository/head/base ownership checks.

Before readiness, the adapter requires PR metadata to report the expected
branch head. It tries up to six reads with delays of 0, 500, 1000, 2000,
4000 and 8000 ms: 15.5 seconds of scheduled pauses plus request time.
The pause is an explicit capability backed by Node's timers/promises in the CLI.
Each attempt checks fresh main/branch refs and the PR's ownership/open state.
Only an otherwise valid PR's head mismatch is retried; API failures, identity
changes, closed PRs or changed refs stop immediately. Exhaustion leaves the
registered draft in place with a specific head-synchronization error.

The adapter re-reads main and branch refs before mutations, including after
the asynchronous head read, disables pending auto-merge while refreshing, and uses
non-force fast-forward updates. New commits have the old owned branch and
current main as parents, with a tree based on current main plus only the five
version files and checkpoint. It never rewrites main or force-pushes a branch.
API/identity/freshness failures stop safely and require reconciliation again.
GitHub's required checks, up-to-date-branch requirement, and human review policy
remain the final merge gate; ref re-reads alone are not a lock against concurrent
human merges. A source that lands immediately after a snapshot is picked up on
the next run, even if the previous version PR has already merged.

### Approve the version PR's CI

[GitHub currently documents](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs)
that `opened`, `synchronize`, and `reopened` PR events created with
`GITHUB_TOKEN` create workflow runs in an **approval-required** state.
A maintainer with write access selects **Approve workflows to run** on the
version PR. Its body repeats this instruction. If the pending branch is
refreshed, inspect and approve the runs for its new head, not only an older run.

The adapter still requests auto-merge, but it does not approve workflow runs,
approve its own PR, or bypass required checks/reviews. Without the human action,
CI and therefore auto-merge can remain blocked. This initial mode is not fully
unattended automation. CI-run approval is separate from PR review, GitHub's
`npm` environment approval, and npm publication approval with 2FA.

GitHub suppresses some token-originated workflow events. Do not rely on a
bot-driven main push always being delivered or always being ignored: if a
follow-up runs, checkpoint exclusion prevents another bump; if an event is
suppressed, manual dispatch remains available to reconcile history. The
automation does not depend on PR-closed events.

### Disable or pause

```sh
gh variable set VERSION_AUTOMATION_ENABLED --body false --repo jderochervlk/rescript-lint
```

This stops **new jobs**; it does not cancel an in-flight run or revoke an
already-pending PR's auto-merge request. If an immediate stop is needed, cancel
the exact active run and disable auto-merge on the identified version PR:

```sh
gh run cancel RUN_ID --repo jderochervlk/rescript-lint
gh pr merge VERSION_PR_NUMBER --disable-auto --repo jderochervlk/rescript-lint
```

Leave its checkpoint and branch intact. Re-enable and manually dispatch to
reconcile merges accumulated while disabled. All npm release actions remain
separate maintainer decisions.

## Recovery and ongoing ownership

After deployment and opt-in, retry with:

```sh
gh workflow run alpha-versions.yml --ref main --repo jderochervlk/rescript-lint
```

Inspect failed runs first. The workflow refuses stale checkouts, checkpoint
drift, unexpected branch writers/files, or identity conflicts. Do not reset IDs,
force-push, or manually merge an unregistered draft. Repair through reviewed
trusted-main changes or an explicitly authorized operator recovery. A closed
unmerged owned PR can be replaced on the same branch; no source is marked
processed until the checkpoint lands in main. Failed CI never merges the PR.
Retain the owned branch or let the adapter recreate it after automatic deletion;
branch deletion is not needed for reconciliation.

If PR creation is forbidden, the run can leave a version branch but does not
change main's checkpoint. Have an administrator inspect the repository's
PR-creation setting, then manually retry; do not reset the branch or source
counts. A draft is registered only once PR creation succeeds.
